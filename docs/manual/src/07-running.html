Running it

Every command and every option; where the records go; what a run records about itself; and how to point Cacophony at a model.

The command line

29 commands. This chapter is the complete reference, grouped by what you are trying to do; appendix F has the same material as a one-page synopsis.

Understanding a schema

validate

cacophony validate PROJECT [--seed N]

Compiles the schema and reports structural problems: unknown generators, bad options, unresolvable dependencies, cycles. Generates nothing.

lint

cacophony lint PROJECT [--strict]

Nineteen rules about schemas that compile and will disappoint you. --strict exits non-zero on warnings as well as errors, which is the form to use in CI. Appendix I lists every rule.

plan

cacophony plan PROJECT [--seed N] [--json]

The compiled truth: entities in dependency order, and per field its generator, cost class, determinism, dependencies and recipe attribution.

prompt

cacophony prompt PROJECT [-e ENTITY] [--batch-size N] [--schema]

Prints the prompts the compiler builds, and with --schema the JSON Schema used to constrain decoding.

generators, recipes, plugins

cacophony generators [--json] cacophony recipes [-p PROJECT] [--show NAME] [--group NAME] [--json] cacophony plugins [--show NAME] [--json]

What is available in this installation: 31 generators, 31 recipes plus whatever the project adds, and any plugins installed.

Producing data

preview

cacophony preview PROJECT [-e ENTITY] [-n COUNT] [--offset N] [-c COLUMNS] [--json] [--isolate] [--cache MODE] [--cache-path FILE] [--seed N]

Shows exactly the records a real run would produce at those indices. --offset looks into the middle of a run you have not done; --isolate draws a different sample when you want variety rather than fidelity.

regenerate

cacophony regenerate PROJECT -r N|N-M [-e ENTITY] [-c COLUMNS] [--json] [--seed N]

Re-derives specific records with no run and no dataset. Refuses more than a thousand and points at generate, which is the tool for that.

Runs

runs, run, resume

cacophony runs [-p PROJECT] [--store FILE] [--state STATE] [--limit N] [--json] cacophony run RUN_ID [-p PROJECT] [--store FILE] [--events N] [--json] cacophony resume [RUN_ID] [-p PROJECT] [--store FILE] [--log-level LEVEL]

Serving

Providers

A provider is a backend that generates something Cacophony cannot compute: prose, pictures or speech. They are declared in the project, referenced by name from fields, and never hold a credential.

providers:
  local_llm:
    type: language_model        # language_model, image, speech, custom
    adapter: ollama
    base_url: http://localhost:11434
    model: llama3.1:8b
    secret: my-secret-id        # a logical id, never a credential
    concurrency: 4
    timeout_seconds: 120
    options:
      structured_output: auto

The generation cache

--cache read_write stores model answers keyed by the prompt and the field's seed, so a re-run costs nothing and a nondeterministic generator becomes reproducible in practice. read_only uses what is there without adding to it. The benchmark forces the cache off, because with it on the second model would be scored on the first model's answers.

Runs

Every generate records a run: what was asked for, what happened, how far it got. The store is SQLite, by default .cacophony/cacophony.db beside the schema file, and it never contains the generated data itself.

$ cacophony generate project.yaml -o parquet -d out/   # ^C at any point
$ cacophony runs                                       # what has been run
$ cacophony run 4f2a91c3 --events 20                   # the inspector
$ cacophony resume 4f2a91c3                            # carry on

What the store holds

Projects, schema revisions, runs, jobs, checkpoints, events and statistics. Every accepted Studio edit creates a schema revision section 73, so a run is always associated with the exact text of the schema that produced it.

What a finished run reports

While a run executes, the numbers come from the process running it: records a second, tokens a second, bytes on disk, an estimate of what is left. When it stops, they come from what it stored — and they stop moving. A finished run's elapsed time is how long it took, not how long ago it was: the two are easy to confuse in an interface, and for a while this one confused them, reporting a minute and counting beside a duration of forty-two milliseconds.

Output size is measured from the files, not counted while writing them. A counter cannot know about a Parquet footer, a compressed page, a partition directory or a SQLite database that four entities shared, and the number people want from "output size" is the size of the output. It is the sum of the run's own files, each counted once, taken after the writers close.

Checkpoints

A job checkpoints after every batch, and the checkpoint holds two numbers rather than one: how many rows have been written, and how far through the source the job has read. Those are the same number only for a schema that neither drops nor duplicates anything. Validation dropping a record and entropy injection duplicating one both make rows-written a poor place to resume from, and a run that resumed there skipped or repeated whatever fell in the gap. There is still no RNG state to serialise: a record's seed comes from its index, so a position is all a resume needs.

On resume the file on disk and the checkpoint are made to agree, exactly. Three things can be true after an unclean stop, and each has its own answer. If the file holds more rows than the checkpoint claims, an appendable file is trimmed back to it — a position whose source index is known. If it holds fewer, the last batch never reached the disk, and the run rewinds to where that batch began, which the checkpoint also records. If they agree, nothing happens. Counting the file and trusting the count, which is what this used to do, answers "how many rows are there" and then uses the answer as "where was the source".

Formats that cannot be appended to

A JSON array and a Parquet file cannot be extended in place, so a resumed run writes a new part: employee.part0001.parquet. Readers for both formats accept a directory of parts. A partitioned output is in the same position whatever its format — a partitioned writer is never appendable, and one that appended into a child file whose last batch was torn would produce exactly the duplicates parts exist to avoid.

A run owns its destination

A writer truncates the file it opens and stops there, so an earlier run's part files and partition directories survive a later run into the same directory and are read back as part of it. One record can arrive in a directory that then reports two. So a fresh run refuses a destination that already holds output it would own, and says what is in the way:

$ cacophony generate project.yaml -d out/
error  out/ already holds output from an earlier run (out/employee.jsonl).
       Generating into it would mix two datasets: the writers replace the files
       they open and leave every other one in place. Choose an empty directory,
       or pass --overwrite to replace what is there.

--overwrite removes exactly what this run would have written — those entities' files, their parts and their partition directories — and never the directory itself, which may be somebody's home. Resuming is unaffected: a resumed run is continuing that output, not competing with it.

Uniqueness across a resume

A unique: true field is checked against the values a run has already produced, and those live in memory, which does not survive the stop. A resumed run therefore reads back what the earlier attempt wrote — from JSON Lines, CSV, JSON or SQLite — before it continues. Parquet and partitioned trees cannot be read back without pulling in the whole dataset, and that is the one thing this program will not do; there the run says so in its events and in its summary, as uniqueness_unverified, rather than implying a check it did not make.

Resuming reuses the original configuration

The same seed, the same format, the same provenance mode, and the schema revision the run started with — recompiled from the revision the store kept, with the project's own directory, so a lookup table beside the schema resolves the way it did the first time. Editing a schema between a stop and a resume changes nothing about the resumed run: it continues the dataset it started. The paths are the run's own, resolved when it began, so resuming from a different working directory continues that dataset rather than starting a second one beside you.

What a run reports while it runs

Section 55's figures, over the socket and in the run row: records and tokens a second, disk throughput, images a minute, audio minutes a minute, progress and an estimate of what is left, per entity and for the run. They are folded in per batch rather than per finished entity, so a single-entity run that takes an hour is not a dashboard of zeros for fifty-nine minutes.

Bytes are attributed to the destination that grew, which matters for SQLite: every entity writes into one database, and asking each writer how large its file is and adding the answers counts the same bytes once per entity. Queue depth is the number of jobs waiting for a worker — a number section 86 asks for, and one this reported as zero for as long as it existed.

One sentence to a world

The design document closes with an image rather than a feature: somebody describes the world they need in a sentence, Cacophony proposes it, they edit the proposal, and then they press a button marked BEGIN CACOPHONY. Every part of that existed separately. This is the flow that joins them.

$ cacophony begin "a small hospital: staff, wards, and admissions over a year"

What it does

  1. Asks a language model for a schema — the same assistant propose uses.
  2. Writes it to a file.
  3. Prints the world it would build: entities, record counts, model calls, media and an approximate size.
  4. Asks.
  5. Hands the compiled project to the same Conductor generate uses.

  note no primary key was proposed for: nurse

BEGIN CACOPHONY? [b]egin, [e]dit, [q]uit (b):

The linter runs on the proposal too, and its findings are part of what you are being asked about. Here it is telling you that nurse has no identifier — harmless for a leaf entity, worth a moment's thought if you were going to reference it later.

e opens the schema in $EDITOR and recompiles it when you come back, as many times as you like — a schema that does not compile puts you straight back in the editor rather than ending the session. q leaves the file where it is.

Two things it insists on

The schema is written before anything is generated. A world that only ever existed in one terminal session is an anecdote. What you get is a project file, a run recorded against it, and cacophony generate <schema> to do the whole thing again on another machine next year.

It asks. A sentence can quite easily describe four hours of work and a hundred gigabytes, so the estimate comes first and the question after it. --yes skips the question for a script, and outside a terminal it is skipped automatically — with a schema that lints clean required, since there is nobody there to fix one that does not.

The bug this flow found on its first run

primary_key is not a required property of a proposal, and a model that omits it produces a schema whose references point at nothing: it compiles, it generates, and it fails on the first join. Cacophony now picks a key for any entity something references — <entity>_id, then id, then the first field ending _id — and marks it unique. "A schema that is known to work" has to include the joins.

What it is not

It is not a different generator, a different engine or a different set of guarantees. Every record it produces comes from the same pipeline as every other record in this manual, and the file it writes is an ordinary project you can edit, lint, bundle, stream, shard across eight machines, or throw away.
